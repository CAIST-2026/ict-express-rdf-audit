## 2. 我新发现的关键问题（原审计未覆盖）

这是本次核查最重要的产出，它推翻了原稿的核心主张。

### 2.1 对齐信息被"直接写进提示词"

`engine.OllamaLLMFilter.make_plan()` 的提示词中，`candidate_entities` 由
`knowledge[canonical]` 构造，而 `knowledge` 来自 `scalable_data.build_llm_memory()` — 即
**同一实体的中英文全部表面形式 + 两个图上的全部 URI 的真值表**。

因此当模拟记忆覆盖某实体时，**正确的跨语言对应 URI 已经在提示词里**，"LLM 对齐"退化为
"从给定候选里挑一个"。

### 2.2 量化结果（`experiments/alignment_probe.py`）

150 条跨语言查询中，**130 条（86.7%）的黄金 URI 逐字出现在提示词中**。按此拆分：

| 组 | n | Hits@1 |
|---|---|---|
| 黄金 URI **在**提示词中 | 130 | **0.500** |
| 黄金 URI **不在**提示词中 | 20 | **0.000** |

解读：

- 把答案递到手上，7B 模型也只有 **50%** 选对 → 所谓"LLM 跨语言对齐能力"其实接近抛硬币。
- 记忆表没覆盖时，成功率 **严格为 0** → 系统的跨语言上限 = 记忆表的覆盖率，而非模型知识。

### 2.3 这直接推翻原稿什么

原稿称"LLM 动态对齐解决跨语言实体识别"。可辩护的说法只能是：

> 在给定真值表面形式表的条件下，7B 规划器对候选的**选择**准确率约 50%；系统的跨语言
> 上界由外部提供的对齐覆盖率决定，而非模型固有的世界知识。

### 2.4 探针的适用范围（已修正，避免过度解读）

提示词只提供**人物**档案。2-hop 的黄金答案是**作品** URI（`W00679A`），需经遍历到达，
故该族标为 `not_applicable`（2-hop 的 0.960 来自"人物对齐 + 两跳遍历"，不是提示词泄漏）。

### 2.5 生成器的设计使"音译基线"结构上不可行

`scalable_data.py` 第 10 行明确写着设计目标："Cross-lingual naming gap — Chinese and English
labels share no characters"。长尾实体的中英标签是**刻意无关**的（如 `朱平` ↔ `Peng LeiTao`），
且 **150 条跨语言查询全部落在长尾 `P` 实体**上。因此拼音音译匹配在该基准上必然接近 0 —
这是数据设计的性质，不是方法优劣。**必须在论文里如实说明，不能当作"我们的方法更好"的证据。**

> 附带影响：该设计也意味着任何**非记忆型**方法（音译、字符串、无监督对齐）在此基准上
> 都不可能成功。基准只检验"是否被提供了对齐表"，对"能否自己推断对齐"没有区分力。
> 这是本工作最重要的局限，也是最好的改进方向。

### 2.6 其余沿用原审计已确认的问题

- `no_aligner` 在同语言族反超完整系统（1.000 vs 0.975/0.960）—— 对齐器在同语言场景有害。
- 旧 `sparql_baseline` 从未真正执行 SPARQL（2-hop 与跨语言均为 0.000）；旧 `vector_graphrag`
  用单语哈希编码器（跨语言 0.000）。二者是**实现缺陷**，不是方法结论 → 已重写为公平基线。
- 旧 `success` 指标与 mock answerer 耦合，近乎同义反复 → 已用不依赖生成器的 `ac1` / `vic` 取代。

## 4. 重写后的定位（本项目的执行依据）

### 4.1 目标读者与场景

面向**在异构知识图谱上构建检索服务**的工程读者：两图 schema 不同、无 `owl:sameAs`、
必须跨语言。关注点不是"模型多强"，而是**"当对齐信息来自外部表时，系统性能的上界与成本结构是什么"**。

### 4.2 研究问题（单一、可证伪）

> 在双语异构 RDF 上，若实体对齐由外部提供的表面形式表支撑，LLM 规划器加上有界图遍历
> 相比真实 SPARQL 与多语言稠密检索，在**严格证据约束的准确率**和**图访问成本**上处于什么位置？
> 其中有多少收益来自模型，多少来自被提供的对齐表？

### 4.3 贡献（全部有数据支撑）

1. **一个不依赖生成器判分的严格指标** `ac1`（黄金实体排首位 **且** 黄金值出现在检索证据中），
   消除原稿中"答案生成器与判分器同源"导致的同义反复。
2. **对齐监督探针**：量化"提示词已含真值"的比例（86.7%），并据此给出**收益归因**
   （在表覆盖内 0.500；覆盖外 0.000）。这是对 LLM-in-the-loop 评估方法的**方法论批评**，
   具有独立价值。
3. **公平基线**：真实 SPARQL 1.1（rdflib 执行，两阶段 + `VALUES` 下推 + 两跳属性路径）
   与多语言稠密检索（e5-small），替换原稿中两个实现受限的"假基线"。
4. **成本结构**：区分串行服务时间、4 并发负载响应时间与吞吐；GSR 明确为**逻辑三元组访问比**，
   **不是**实测 I/O 或内存节省。LLM 延迟主导端到端时间（2-hop 均值约 28 s）。
5. **边界陈述**：跨语言收益来自被提供的对齐表；在"标签刻意无关"的合成数据上，非记忆型方法
   结构上不可能奏效 —— 因此结论**不可外推到真实世界跨语言对齐**。

### 4.4 与前人工作的区别

不是"又一个 GraphRAG"，而是**对 LLM-in-the-loop KG 检索评估有效性的检验**，并附带一个
在该设定下成本可控的检索管线。批评性 + 建设性。

### 4.5 保留 / 删除清单

**保留**：`outputs_audit` 主结果；多种子与配对检验；覆盖率消融；严格指标；真实 SPARQL；
多语言稠密基线；延迟三协议；规模实验（补跑）。

**删除/改写**：
- 删除："ICT 平台部署""真实场景验证""LLM 具备跨语言世界知识"。
- 改写：GSR 一律称"逻辑访问比"；基线结论改为"该实现受限"，不说"SPARQL/向量方法失败"。
- 删除：DBP15K 相关表述（它只支持实体对齐子任务，不能验证端到端检索；本次未运行，不得声称）。

### 4.6 证据边界（论文必须写明）

- 全部结果来自**合成**双语 RDF（49,781 三元组），**无任何真实 ICT 数据**。
- "LLM"是本地 qwen2.5:7b + **模拟记忆表**；记忆表覆盖率是**输入参数**（0.92），不是测量值。
- 判分不含 LLM-as-judge 的独立人工一致性验证 → 不声称"人工标注一致"。
- 单机、单模型、单数据集；无跨数据集泛化证据。
